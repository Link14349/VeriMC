# VMCB 二进制电路格式

版本：1.0，2026-09-07。扩展名：**`.vmcb`**，名称为 VeriMC Circuit Binary。

**已接入 simulator 原生读写和浏览器工程菜单，默认使用 `.vmcb`，继续兼容旧 JSON 导入和显式导出。** 本文定义字节协议；第 11 节区分已验证范围和后续验收项目，规模结果见 [文件实测](vmcbFiles.md)。

## 1. 目标与取舍

默认保存格式面向几十万至几百万个方块：方块名称和属性只在状态表中保存一次；空间按 16×16×16 分区；分区根据内容选择整区填充、位打包、稀疏或游程编码，再独立压缩。只记录非空分区，不存包围盒中的大片空气。

采用自有二进制容器。布局采用专用编码；元数据和可变结构采用 CBOR；压缩采用 Zstandard。不把整份旧 JSON 包进二进制文件，也不为每个方块保留一份名称、属性及三维坐标。

16³ 与当前 `World` 的存储单元一致，方便逐区读写。文件目录支持按坐标定位分区；这只是文件读取能力，**不表示仿真可以随意卸载相邻区域**。执行仍须满足完整依赖和加载区域规则。

扩展名统一为 `.vmcb`，用文件头区分两种内容：

| 类型 | 建议文件名 | 含义 |
| --- | --- | --- |
| 电路设计 | `加法器.vmcb` | 布局、初始库存/环境、探针及明确的初始化策略；从头启动 |
| 运行快照 | `加法器.snapshot.vmcb` | 当前布局和精确执行现场；从保存位置续跑 |

`.snapshot` 只是便于人识别的文件名部分；程序必须检查文件头，不能靠文件名决定语义。VMCB 不是 Litematic 或 Create 蓝图格式，不保存游戏 JAR，也不引入 HDL 编译功能。

## 2. 基础编码

- 下文自定义字段的 `u16/u32/u64/i32` 均为固定宽度、小端序；`i32` 为二进制补码。禁止直接写入 C++ 结构体内存、指针、`size_t`、枚举对象或位域。
- `varU32` 为最短形式的无符号 LEB128，每字节低 7 位为数据、最高位为续接标志。最多 5 字节；第 5 字节的数据不超过 15。拒绝溢出、截断及非最短形式。
- `string` 为 `varU32` 字节长度加 UTF-8 字节，不含终止零。无效 UTF-8 拒绝；不暗中做 Unicode 规范化。Minecraft 名称保存完整命名空间，属性键和值均保存字符串。
- 自定义位流按最低有效位优先：第 `j` 个编号的第 `t` 位放到位流位置 `j*b+t`。字节内 bit 0 最先使用；可跨字节；末字节未使用的高位必须为零。不能使用原版某一代 NBT long 数组的隐式对齐规则。
- CRC 使用 CRC-32/ISO-HDLC：反射多项式 `0xEDB88320`，初值及末异或均为 `0xFFFFFFFF`；`123456789` 的校验值为 `0xCBF43926`。CRC 只用于损坏检测。
- CBOR 字段遵循 CBOR 自己的字节序，**不套用上述小端规则**。采用 [RFC 8949 §4.2.1](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.1) 的确定性编码：确定长度、最短无损编码、按编码后键字节排序。VMCB 限定 map 键为文本；拒绝重复键、tag、undefined、非有限浮点值和尾随数据。保留整数/浮点类型差异及浮点负零；64 位整数不能经过 JavaScript Number。

## 3. 容器布局

```text
64 字节文件头
数据段 0
数据段 1
...
数据段 N-1
N × 64 字节目录
EOF
```

没有隐式对齐或填充。偏移以文件起点为零。写入器先顺序写数据、再写目录，最后回填文件头；通过临时文件形成完整成品后再提供下载或原子替换目标文件。

### 3.1 文件头（64 字节）

| 偏移 | 字段 | 类型 | 规则 |
| ---: | --- | --- | --- |
| 0 | magic | byte[8] | `56 4D 43 42 0D 0A 1A 0A`，即 `VMCB` 加二进制识别尾缀 |
| 8 | formatMajor | u16 | 1 |
| 10 | formatMinor | u16 | 0 |
| 12 | headerBytes | u16 | 64 |
| 14 | entryBytes | u16 | 64 |
| 16 | flags | u32 | bit 0：0=电路，1=快照；其余为 0 |
| 20 | entryCount | u32 | 目录项数 |
| 24 | directoryOffset | u64 | 目录起点 |
| 32 | directoryBytes | u64 | 必须等于 `entryCount * 64` |
| 40 | fileBytes | u64 | 实际文件总长 |
| 48 | nonAirCount | u64 | 所有 BLKS 的非空气方块数之和 |
| 56 | directoryCrc | u32 | 原样目录字节的 CRC |
| 60 | headerCrc | u32 | 文件头 `[0,60)` 字节的 CRC |

必须满足 `directoryOffset + directoryBytes == fileBytes == 实际 EOF`。所有长度加乘运算先检查溢出。`formatMajor` 不同直接拒绝；同一主版本的新增功能按数据段版本和 critical 标志判断，不能仅因次版本较大就无条件接受。

### 3.2 目录项（64 字节）

| 偏移 | 字段 | 类型 | 规则 |
| ---: | --- | --- | --- |
| 0 | tag | byte[4] | ASCII 段类型，如 `BLKS` |
| 4 | schemaMajor | u16 | 该段的数据结构主版本，首版为 1 |
| 6 | schemaMinor | u16 | 首版为 0 |
| 8 | flags | u32 | bit 0=critical；其余为 0 |
| 12 | codec | u8 | 0=原样；1=Zstandard |
| 13 | reserved | byte[3] | 全零 |
| 16 | sectionX | i32 | 空间分区坐标；非空间段为 0 |
| 20 | sectionY | i32 | 同上 |
| 24 | sectionZ | i32 | 同上 |
| 28 | partIndex | u32 | 同类、同坐标段的分片号，从 0 连续递增 |
| 32 | dataOffset | u64 | 存储数据起点 |
| 40 | storedBytes | u64 | 存储长度，必须大于 0 |
| 48 | rawBytes | u64 | 解压后长度，必须大于 0 |
| 56 | rawCrc | u32 | 解压后字节的 CRC |
| 60 | reserved | u32 | 0 |

目录按 `(tag 字节序, sectionX, sectionY, sectionZ, partIndex)` 升序排列，坐标按有符号整数比较，键不得重复。按 `dataOffset` 排序后，各段必须不重叠、无间隙地覆盖 `[64,directoryOffset)`；目录本身不压缩。分片仅用于下表允许的段，不能将一个 BLKS 分区拆开。

未知 critical 段、已知段的未知主版本、未知压缩方法或保留位非零，拒绝正常导入。未知非关键段可以跳过解释，但在未编辑的转存中必须原样保留；不能无声丢失它。若编辑后无法保证其有效性，阻止覆盖原文件，明确报告该扩展需要迁移。影响物理、初始化、队列或探针采样语义的段一律必须 critical。

当前读取器采取保守策略：只接受文件/段版本 1.0、表中八种已知 critical 段；遇到未知非关键扩展也明确拒绝，尚不提供不透明扩展保留与转存。拒绝不会改动当前工程。

### 3.3 数据段清单

| tag | 内容 | 键与数量 | critical |
| --- | --- | --- | --- |
| META | 工程/版本/初始化元数据，CBOR map | 全局，恰好 1 个，part=0 | 是 |
| PALT | 文件级方块状态表，专用二进制 | 全局，恰好 1 个，part=0 | 是 |
| BLKS | 16³ 分区布局，专用二进制 | 每个非空分区 1 个，part=0 | 是 |
| BDAT | 器件库存、环境及内部数据，CBOR 行数组 | 按分区，可分片；无记录时省略 | 是 |
| ORDR | 方块实体持久执行顺序，专用二进制 | 全局，可分片；至少 1 个 | 是 |
| PROB | 探针配置，CBOR 行数组 | 全局，可分片；至少 1 个 | 是 |
| RUNT | 快照队列和运行表，CBOR map | 全局，可分片；电路禁止，快照至少 1 个 | 是 |
| TRCE | 已保留的采样历史，专用二进制 | 全局，可分片；电路禁止，快照至少 1 个 | 是 |

空电路仍须有 META、PALT、ORDR、PROB，`nonAirCount=0`，没有 BLKS 和 BDAT。空数组/空表必须有实际编码，不能使用零字节数据段。视图、分组、HDL 源码映射、输入时间线/放置历史扩展留给单独的带版本数据段；**首版没有定义这些段，不能宣称已保存**。需要历史才能恢复的现场使用快照。

## 4. META：版本与初始化

以下是 CBOR 的可读示意，文件中不写 JSON 文本。每个键均必需，只有 `snapshot` 为快照专用：

```text
name: string
edition: "java"
minecraftVersion: "26.2"
referenceServerSha1: "823e2250d24b3ddac457a60c92a6a941943fcd6a"
writerVersion: string
rulesDigest: 32 字节的 CBOR byte string
profile: {experimentalRedstone: false, naturalRandomTicks: false, loadedRegionOnly: true}
origin: [i32, i32, i32]
initialization: "canonicalXYZ1" 或 "checkpoint1"
randomSource: {algorithm: "javaLegacy48", seed: u64}
nextEntityOrder: u64
snapshot: { ... }  // 仅快照
```

参考版本来自仓库的 [referenceVersion.json](../data/referenceVersion.json)，固定为 Java 26.2。`rulesDigest` 的输入是本实现实际使用的七个规则文件：`blockStates.json`、`compostingRules.json`、`itemDefinitions.json`、`jukeboxRules.json`、`noteRules.json`、`referenceVersion.json`、`vibrationRules.json`。按上述文件名字节升序，对每个文件连接 `string 文件名 + SHA-256(原始文件字节)`，再计算整个串的 SHA-256。文件清单的变化需要新的规则身份；不能漏掉影响行为的数据。

`rulesDigest` 约束数据，不能替代引擎行为版本。快照的 `snapshot` map 必须包含 `checkpointAbi: "simulatorCheckpoint1"` 和 `engineBuild: string`：前者标识经过续跑验证的执行语义/快照结构，后者记录实际构建。改变可观察执行语义必须更新 ABI；同 ABI 的构建只有通过续跑对照才允许互读。当前读取器检查 ABI；构建指纹由实际核心源码、头文件及编译器身份计算，供追溯使用，不要求指纹逐字相同。

版本、参考构建、规则设置或 rulesDigest 不匹配时，不自动运行；返回明确的迁移错误。快照还必须匹配 checkpointAbi。迁移工具需要单独做兼容验证，不能通过忽略检查强行加载。

`origin` 是工程标记的参考原点，默认 `[0,0,0]`。布局和所有器件/探针/事件坐标始终使用绝对 Minecraft 方块坐标；导入不自动平移，origin 不二次叠加到坐标上。

### 4.1 电路初始化

`initialization="canonicalXYZ1"` 对齐现有 `loadProject`：先无副作用装入全部布局、初始器件数据与 ORDR；随后严格按绝对坐标 `(x,y,z)` 升序调用初始化，再按同一顺序发邻居通知。两轮执行之间保留现有唱片库存启动步骤；初始时间为 0，随机源由 seed 初始化。不得按文件分区顺序、解压完成顺序或哈希表顺序发更新。该策略必须经现有 JSON 导入对照验证后冻结。

方块状态按文件保存，但初始化可能依法改变状态；不能宣称只存静态布局就能还原任意 BUD、瞬态或原始搭建过程。正在运动的活塞、在途振动/冷却感测体、待处理外部动作、等待演奏的音符盒和摆动的钟，继续沿用现有电路导出拒绝条件，提示保存快照。其他依赖执行历史的电路也应使用快照。

### 4.2 快照元数据

`initialization="checkpoint1"`。`snapshot` 还必须包括：`tick`、`nextOrder`、`sequence`、`nextProbeId`、`nextActionId`、`actionsDropped`、`traceDropped`、`traceCapacity`、`traceAtomicReserve`、`updateBudget`、`blockTickEarliestCollection`，均为 u64；以及 `faulted: bool`、`randomState: u64`、`randomDraws: u64`。随机内部状态限定为 48 位，tick 不允许 `UINT64_MAX`。

恢复快照直接装入状态和队列，不执行电路初始化，不重排已有批次。恢复后保持暂停，外部动作未完成、探针背压等条件重新核验。`faulted=true` 的记录仅供检查，正常可运行导入拒绝。重建显示修订号和连接游标，不恢复过期浏览器会话；不能因此丢弃探针记录或未处理动作。

## 5. PALT：文件级方块状态表

```text
varU32 stateCount
重复 stateCount 次：
    string blockName
    varU32 propertyCount
    重复 propertyCount 次：string propertyName, string propertyValue
```

编号由条目次序产生，从 0 开始。0 必须是无属性的 `minecraft:air`。其余只写文件实际引用的状态，包括活塞正在搬运的状态和振动关联状态；按名称 UTF-8 字节序、再按排序后的属性键值对字典序排序。每条属性按键字节序排序，不允许重复属性、重复完整状态或省略原版要求的属性。

同名方块的不同朝向、强度、延迟等是不同状态。读取时用完整名称和属性解析成当前原生 `StateId`，之后分区直接映射编号，不反复解析字符串。不得把程序内部 `StateId`、`TypeId` 或 `Device` 枚举当成永久文件编号；未知名称/属性必须报错，布局中的未实现器件也必须报错，不能改成空气。已知但未实现的状态可仅作为外部振动的 affectedBlock 上下文保存，这不意味着实际放置或仿真该器件。`cave_air` 等原版标识也不能不经语义定义就折叠成 `air`。

## 6. BLKS：空间布局

对每个轴使用数学下取整：`sectionX=floor(x/16)`，`localX=x-16*sectionX`，其他轴相同。局部坐标均为 0–15。

```text
localIndex = localX | (localZ << 4) | (localY << 8)
x = 16*sectionX + (localIndex & 15)
z = 16*sectionZ + ((localIndex >> 4) & 15)
y = 16*sectionY + (localIndex >> 8)
```

例如 `(-1,-17,16)` 属于 `(-1,-2,1)`，局部坐标为 `(15,15,0)`，localIndex=3855。乘法与加法在检查过的 64 位临时整数中完成，再检查坐标范围。格式可表达 i32 坐标，首个 simulator 读入策略仍限定各轴 `±29999984`；不能用文件格式升级默默放宽内核边界。

### 6.1 分区公共头与局部状态表

| 偏移 | 字段 | 类型 |
| ---: | --- | --- |
| 0 | mode | u8 |
| 1 | bitsPerIndex | u8 |
| 2 | nonAirCount | u16，1–4096 |
| 4 | paletteCount | u16，1–4096 |
| 6 | reserved | u16，必须为 0 |
| 8 | palette | `paletteCount` 个 varU32 文件状态编号 |
| 可变 | 数据 | 由 mode 决定 |

局部状态表按文件状态编号升序，编号从 0 开始；只含该编码实际引用的状态。空气不强制占用一个条目。`bitsPerIndex=ceil(log2(paletteCount))`，单状态时为 0。全部引用必须在范围内；解码后重新计算 nonAirCount，与分区头及文件总数核对。

### 6.2 四种编码

| mode | 名称 | palette 的内容 | 数据 |
| ---: | --- | --- | --- |
| 0 | uniform | 恰好一个非空气状态 | 无；4096 格全部为该状态 |
| 1 | packed | 全部实际出现状态，部分空分区须含空气 | 4096 个局部编号的位流 |
| 2 | sparse | 只含实际出现的非空气状态 | N 个空隙 varU32，随后是 N 个局部编号位流 |
| 3 | runs | 全部实际出现状态，部分空分区须含空气 | varU32 段数 R；R 个长度减一 varU32；R 个局部编号位流 |

`uniform` 必须满足 N=4096、paletteCount=1、bits=0。其他模式允许单状态时零长度编号位流。reader 接受合法但非最小的模式；writer 必须比较合法模式的**完整未压缩长度（含各自状态表）**，选择最短，相同长度取 mode 较小者。

`packed` 按 localIndex=0…4095 编码，字节数为 `ceil(4096*b/8)`。

`sparse` 按非空气 localIndex 递增，初始 previous=-1，每个空隙为 `current-previous-1`；解码为 `current=previous+1+gap`。每个位置必须小于 4096，不能重复。读完 N 个空隙后，后续 `ceil(N*b/8)` 字节是对应状态编号；其余格为空气。因此单状态稀疏区不需要逐方块写状态编号。

`runs` 按同一 localIndex 顺序覆盖全部 4096 格，R 为 1–4096；每个长度解码后至少为 1，总和必须等于 4096。相邻游程不能使用相同状态。编号位流长 `ceil(R*b/8)` 字节。

不存全空分区。BLKS 记录内容必须恰好耗尽 rawBytes，不能有尾随字段。布局按分区排序便于随机读取，但不得用这个顺序替代第 4.1 节的初始化顺序。

### 6.3 最小字节示例

以下只表示 BLKS 原始 payload，不含容器头、目录及 PALT；示例假设所引用文件状态非空气且存在：

```text
全区填充状态 7：
00 00 00 10 01 00 00 00 07

只有 localIndex=0、4095 两格为状态 5：
02 00 02 00 01 00 00 00 05 00 FE 1F
```

第一例共 9 字节。第二例共 12 字节：空隙为 0、4094，状态表只有一个值，因此没有编号位流。单独的位打包示例：b=2、编号 `[0,1,2,1]` 编成 `64`（十六进制）。

## 7. 器件、顺序、探针与运行数据

### 7.1 BDAT

每段为 CBOR array，记录为 `{localIndex, values, inventory?, output?}`。器件类型由 BLKS 推导；记录按 localIndex 排序，分片串联后仍须严格递增，同一位置不能重复。只能引用本分区中存在的方块。

`values` 是当前器件文档与 `validateRuntime` 定义的属性 map；`inventory` 是按 slot 升序的非空槽数组，每项 `{slot, item, count}`，item 使用完整 Minecraft 名称，不写本机 ItemId。省略 inventory 或省略某个槽表示该容器槽为空，不表示未加载。组件未实现时仍拒绝，不能丢弃组件后导入。器件状态、槽位范围、过滤与堆叠上限继续接受内核校验。

电路只保存初始值，继续排除音符盒播放诊断、钟摆动等运行信息；快照记录 output 和完整内部值。每种器件语义发生不兼容改变时，更新段版本或 checkpointAbi，不能继续沿用版本 1 去解释不同的值。器件的完整校验规则以对应专题文档及接入时冻结的 schema 为准；容器协议本身不授予未实现器件支持。

BDAT 按分区分页而不是聚合成百万项 CBOR/JSON DOM。Zstandard 可压缩段内重复字段与物品名称；首版不另外定义物品/任意字符串全局字典，避免不必要的跨段依赖。库存占比高时，仍须单独测量其体积和内存。

### 7.2 ORDR

每段为 `u32 rowCount`，随后 rowCount 条固定 20 字节记录：`i32 x, i32 y, i32 z, u64 order`。各片串联后按 order 严格递增，位置与 order 均不可重复，order 必须小于 META.nextEntityOrder。

这是已有 `entityOrder`，同时用于电路及快照；只允许需要持久方块实体顺序的器件。它与布局存储顺序无关。缺失应有记录、引用不适用器件或顺序冲突均拒绝，不自动按坐标重新分配快照顺序。

### 7.3 PROB

CBOR 数组，记录字段对应现有 `id, pos, name, mode, direction, trigger, triggerValue`。保留原数组顺序，id 唯一；position 为三元素整数数组，方向用稳定字符串。快照额外要求 lastValue；电路启动后重新采样。探针可以位于空气上，不能按 BDAT 的存在性规则拒绝。

### 7.4 RUNT

把当前快照的大数组拆成命名表。每片为 `{table: string, rows: array}`，目录 partIndex 跨全部 RUNT 片从 0 连续递增；表按下列名字的 UTF-8 字节序排列，同一表的片必须连续。每张表至少一片，空表用空 rows，不能靠“没保存”猜测“没有状态”。

| table | 对应内容与顺序 |
| --- | --- |
| blockTickBatch | 当前刻已经收集的计划刻批次，保留原队列顺序 |
| environmentActions | 外部动作历史、未确认状态，按动作 id 顺序；不重新发出已确认动作 |
| events | 未来计划刻、方块事件、方块实体/环境阶段事件，保留完整执行键 |
| hoppers | 漏斗冷却、首次执行、唤醒、代数，按绝对坐标排序 |
| jukeboxes | 唱片、播放进度、唤醒与代数，按绝对坐标排序 |
| motions | 活塞搬运、方向、进度、代数及 lastTicked，按绝对坐标排序 |
| sensors | 振动候选/在途内容、距离、来源上下文、唤醒等，按绝对坐标排序 |
| torchToggles | 世界级火把历史，按现有时间顺序，同刻保持原顺序，包括已拆除位置 |

行字段继承当前 `saveProject(true)` 的同名表，`blockTickBatch` 对应 `blockTickState.batch`，其 earliestCollection 移到 META。下列编码转换必须显式执行：事件 `type` 改为 `blockName`；motion 的 `movedState` 改为文件 PALT 编号；振动的 affectedBlock 改为可选 `affectedPaletteId`；song/game event/item 保留完整名字；时刻、顺序、代数和随机计数使用无损整数。无需唤醒使用 CBOR null，不通过浮点 UINT64_MAX 表示。

events 和 batch 的行都保留 `tick, priority, order, pos, blockName, phase, data, entityOrder`。phase 固定为现有语义的 0=计划刻、1=方块事件、2=方块实体、3=环境接触。events 按当前执行键 `(tick, phaseRank, priority, entityOrder 或 order, order)` 排序，其中 phaseRank 对 phase 0/1/2/3 分别为 0/1/3/2，第四项仅在 phase=2 时使用 entityOrder；batch 保留原批次顺序，不能再次按这个键排序。若新增执行阶段或改变 data 的位语义，必须变更 checkpointAbi。跨表的计数、去重键、对象类型、唤醒时刻与代数必须一致；不能在导入时“修复”为另一条执行轨迹。

### 7.5 TRCE

每段为 `u32 rowCount`，随后 rowCount 条固定 25 字节记录：`u64 probeId, u64 tick, u64 sequence, u8 value`。无填充，value 限定 0–15。按保存的历史顺序串联，保留同刻多个边沿；不能只留每刻最后一个值。删除探针后遗留的历史仍按现有规则保存，不能静默裁剪。

计数与历史截断信息来自 META；快照不必保存已因历史预算而丢弃的过去记录，但必须保留准确的 traceDropped。读取器容量不足时返回预算错误，不丢掉记录后继续宣称精确恢复。把波形分段便于流式读取，并不增加波形采样率或改写游戏刻。

## 8. 压缩、限额与损坏处理

codec=1 使用 [RFC 8878](https://www.rfc-editor.org/rfc/rfc8878.html) 的**单个独立 Zstandard frame**。不使用外部字典、skippable frame 或帧拼接；必须声明与 rawBytes 相等的 frame content size，解压窗口最多 8 MiB。不要把整份 VMCB 再整体压缩，否则目录不能直接定位数据。codec=0 必须满足 storedBytes=rawBytes。

默认写入参数为 Zstandard level 3。每段尝试压缩后，只有结果严格小于原样数据才使用 codec=1，否则存 codec=0；压缩器版本和级别影响字节大小，不影响格式语义，不能把不同版本的压缩字节相等作为跨版本承诺。

当前读取器采用以下预算。原生 `ProjectFileOptions` 可配置文件字节数、非空气方块数、候选内存预估及进度回调；其他结构上限固定。服务使用默认值：

| 项目 | 初始策略 |
| --- | --- |
| 文件大小 | 8 GiB |
| 单段 rawBytes / storedBytes | 各不超过 8 MiB，超限表按行分片；单行仍超限则拒绝 |
| 全部 rawBytes 之和 | 4 GiB，解压前核验，不因压缩率高而放宽 |
| 目录项 | 2,000,000 |
| PALT | 262,144 条，且仍受单段预算约束 |
| 普通字符串 | 每项最多 64 KiB，工程名称最多 16 KiB |
| CBOR | 深度最多 32，每段最多 1,000,000 个值（含键和容器） |
| 非空气方块 | 当前内核保持 2,000,000；格式的 u64 总数字段不是承诺能加载更多 |
| 计划事件 | 当前内核保持 2,000,000，同时计算 batch 和其他队列所需内存 |
| 候选世界额外内存 | 默认 2 GiB 预估：`分区数×33000 + 目录项数×256 + rawBytes 总量×16 + 256 MiB`；这是保守预检，不是操作系统硬限额 |
| 快照采样与更新预算 | traceCapacity + traceAtomicReserve ≤ 2,000,000；updateBudget 为 1…2,000,000 |
| 旧 JSON | 原始长度不超过候选内存预算的 1/12，并检查嵌套/节点数/重复键；默认约 170 MiB |

极端稀疏世界即使只有少数方块，也可能创建大量内存区块。预估内存必须使用**非空分区数**和当前 World 区块分配成本，不能只用 nonAirCount 乘几字节。不得在未检查目录、预算及长度之前按声明值 reserve 大缓冲。

读取先校验头/目录 CRC，再检查偏移、版本、必需段及资源预算，随后逐段检查实际解压长度、CRC、结构与语义。记录出错段、坐标、偏移和原因。CRC 失败、未知关键数据、重复分区/位置、越界编号、截断位流、非法长度均终止正常导入。损坏恢复若以后提供，必须作为明确的不完整检查功能，不能加载残余块后当成原电路运行。

## 9. C++ 与浏览器的接入方案

### 9.1 原生读取和写入

独立格式适配层为 `include/simulator/vmcbFormat.hpp`、`src/vmcbFormat.cpp` 和 `src/vmcbEncoding.cpp`；核心不依赖 HTTP。按流/文件读取 payload，状态表解析一次；布局直接交给候选 World，不先还原百万个 JSON 对象。

拆分现有 `project.cpp` 的结构装载和语义验证，让旧 JSON 与 VMCB 共用验证及初始化路径。不得以 `saveProject → 完整 JSON → CBOR` 实现默认导出，也不得以 `VMCB → 完整 JSON blocks → loadProject` 实现默认导入。小段器件数据可以逐片使用现有 Json 值结构桥接，但片处理完就释放；不能再汇总为完整工程 DOM。

World 增加只读分区遍历入口，导出只需 O(状态表 + 分区索引 + 单段缓冲) 的格式工作内存，布局写入不调用 `world.cells()` 构造、排序百万项数组。初始化仍需按绝对 XYZ 遍历，使用有序分区/局部坐标遍历或有界归并来满足第 4.1 节，不能把逐分区遍历误当作全局 XYZ。

当前已共享 `ProjectSource/ProjectSink` 语义路径。布局按区编码；表按目标 512 KiB 分页，最大 8 MiB。以上布局缓冲复杂度不包含目录、服务导出的原生世界副本、运行表索引/事件排序及最终候选世界。电路的两轮初始化及其间的唱片启动步骤，每次遍历各使用一份稳定的原生 World 副本，保证过程中新增/移除方块不会改变本轮遍历集合。

导入在独立 candidate 中完成所有校验。成功时在仿真线程一次性交换世界、运行状态、工程名称及撤销历史；失败或取消保留原工程和撤销/重做历史。导出锁定一个明确的修订号及事件边界，首版可以暂停世界写临时文件；暂停不是跨线程读可变世界的同步机制，工作线程若参与，必须通过所有权交接或不可变快照访问。

解析/压缩长任务在单线程工作队列执行并提供阶段进度，控制通道仍能处理取消和状态查询。当前采用私有临时目录，完整写入并关闭后才发放浏览器下载，不提供直接覆盖用户磁盘路径的接口。未来若增加路径保存，需同目录临时文件后原子替换；崩溃持久性还需目标平台的文件及目录同步。失败不能留下被误识别为成功的新文件。

### 9.2 文件传输与界面

浏览器只上传/下载原始文件字节，C++ 负责解析和编码。WebSocket `importFile/exportFile` 建立任务，`cancelFile/fileStatus` 控制任务；HTTP `POST /api/files/{id}/upload` 用 64 KiB 缓冲落盘，`GET /api/files/{id}` 查询进度，`GET /api/files/{id}/download` 流式下载。端点检查 Host、Origin 和会话令牌；上传/查询用请求头，直接下载链接使用查询参数。原有 WebSocket 消息上限不需要随工程文件放大。

上传以有界缓冲写临时文件，下载流式发送已经完成的临时成品；文件访问限于本次会话发放的标识，不接受任意本地路径。下载使用 `application/octet-stream` 和带 `.vmcb` 文件名的 `Content-Disposition: attachment`，不冒称已注册专用 MIME。下载应使用浏览器直接文件下载响应，避免前端必须把几 GiB 完整聚成 ArrayBuffer/Blob。上传/下载中断清理临时文件，失败或取消不会改动当前工程。

工程菜单默认“导出电路 .vmcb”“导出运行快照 .vmcb”；导入接受 `.vmcb` 和旧 `.json`，以 magic/实际内容核验格式。旧 JSON 由原生解析器直接读取并迁移，不再让浏览器 JSON.parse 后重发，以免 u64 经过 Number 丢精度。迁移另存 `.vmcb`，保留原文件；旧快照缺少必要版本身份时不能猜测身份并宣称精确迁移。

JSON 可保留为显式的调试/可读导出，默认保存改为 VMCB。大文件进度包含“上传、校验、解压、构建、初始化/恢复”等阶段。工程替换后场景订阅也需分批刷新；文件小不代表浏览器可一次渲染百万方块，现有完整场景发布瓶颈要独立验收。

当前界面提供电路/快照两种旧 JSON 导出。旧 JSON 沿用既有格式及语义校验，没有 VMCB 的规则摘要和 ABI 证据，不能据此保证任意历史引擎版本精确续跑。等待上传超过 60 秒取消；临时下载在创建后 15 分钟过期，最多保留 8 个任务。长任务期间暂停仿真并阻止编辑；前端进度覆盖层支持取消。服务导出前复制世界、完成导入后发布整个场景仍可能造成短暂停顿，这部分不属于已完成的分页文件优化。

## 10. 体积预算

以下是**未压缩布局和 BLKS 目录的精确算式**，不是已测得的完整文件大小，也不是运行性能。统一取 1,048,576 个非空气方块（约 105 万），所用文件状态编号均小于 128；不计 META/PALT/ORDR/PROB、器件数据、快照、对应额外目录及压缩结果。单位 MiB=1,048,576 字节。

| 布局 | 非空分区数 | 编码与每区 payload | 加 64 字节文件头及每区 64 字节目录 |
| --- | ---: | --- | ---: |
| 每区全部为同一种方块 | 256 | uniform：9 字节 | 18,752 字节，约 0.018 MiB |
| 每区填满、16 种状态交错 | 256 | packed：`8+16+4096*4/8=2072` 字节 | 546,880 字节，约 0.522 MiB |
| 每区半空、8 种非空气状态混排 | 512 | packed 含空气：`8+9+4096*4/8=2065` 字节 | 1,090,112 字节，约 1.040 MiB |
| 每区 64 个同状态方块，索引为 0、64…4032 | 16,384 | sparse：`8+1+64=73` 字节 | 2,244,672 字节，约 2.141 MiB |
| 每区仅 1 个方块，索引均为 0 | 1,048,576 | sparse：`8+1+1=10` 字节 | 77,594,688 字节，约 74.000 MiB |

表中 mixed 布局选择没有更短游程的分布。局部“状态数”包含不同朝向、强度等属性组合，不能只数方块名称；超过 16 种时可能需要 5 位以上。最后一行说明极端稀疏布局的目录占用，且按当前 World 分配方式可能先触及内存预算，不能据压缩文件大小保证可运行。

对常见连续结构，主要收益来自状态表复用、省略重复坐标和位打包，压缩在此基础上进一步尝试；不承诺所有百万方块电路都小于 1 MiB。真实大小必须加入库存、初始化信息、队列和波形，实测后记录。

## 11. 实现验收

后续回归和完整规模验收继续覆盖下列项目：

1. 固定字节向量覆盖头/目录、CRC、四种布局、跨字节编号和负坐标；另一个独立读取器交叉验证，避免仅用同一读写器往返掩盖对称错误。
2. 旧 JSON 与 VMCB 的布局、完整状态、库存、环境、探针及实体顺序一致；电路初始化的完整事件流对照一致，覆盖分区顺序与 XYZ 顺序不同的场景。
3. 快照在按钮释放、计划刻批次中途、活塞移动、漏斗冷却、在途振动、唱片播放、火把历史及外部动作等待时保存续跑，与不中断执行逐事件对照。
4. 覆盖 `2^53` 以上计数、u64 边界、null 唤醒、负零/浮点距离；状态表重排后仍正确映射，未知状态/不兼容 ABI 明确拒绝。
5. 截断、位翻转、错误 CRC、越界/重叠目录、解压超额、重复键/分区、非法 varint/位流、遗漏关键表、未知版本、取消导入与写盘失败；验证原工程及历史不变。对解析器做模糊测试并跑 ASan/UBSan。
6. Release 测量 10 万、100 万、200 万方块的稠密/稀疏/容器密集布局与快照：完整文件字节数、读写耗时、峰值内存、临时磁盘占用、控制响应与取消延迟。记录硬件、构建、状态数、分区数、器件/队列/波形规模、压缩器版本与级别。
7. 与现有缩进 JSON、紧凑 JSON、压缩 JSON 比较相同语义数据，避免把去掉空白或省略历史算成专用格式收益；往返校验结果同时记录。

当前证据：83 项既有核心测试与 11 组 VMCB 测试通过 Release 和 ASan/UBSan；固定字节向量和独立 Python 读取器交叉验证。VMCB 测试覆盖四种编码、负坐标、CBOR 数值、旧 JSON 大整数、初始化对照、按钮、部分执行批次、移动活塞、火把历史、库存/漏斗、外部动作、振动、钟/音符/唱片快照及损坏/取消原子性；部分执行批次逐事件对照，其余场景比较完整状态与续跑终点。250 次位翻转属于小规模确定性变异检查，不等同于持续覆盖率引导模糊测试。

文件协议测试覆盖两种格式、撤销/重做、损坏、空电路、取消、截断上传、8 GiB 上限、长文件名和会话检查；浏览器实操验证快照导入与默认下载，控制台无错误。已记录稠密 10 万/约 105 万/200 万方块、稀疏约 105 万方块及 1 万有库存容器的 Release 单次往返，并对较小样本比较紧凑/缩进/压缩 JSON。大型动态快照、持续模糊测试、磁盘故障注入、取消延迟和百万方块浏览器刷新仍待专项测量，不据当前文件测试宣称完成。
