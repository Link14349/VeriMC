# 库存模型

当前开放普通箱子、陷阱箱、木桶。漏斗已支持箱子、木桶和漏斗之间的传输。铜箱、潜影盒、投掷器、发射器和加工器件仍在扩展，未完成的器件不会进入可放置器件库。

## 实际库存

原生内核按物理方块保存槽位，单槽由物品索引和数量构成；没有物品的容器不预分配库存数组。1,537 种默认物品的堆叠上限来自 Java 26.2 物品组件报告。

比较器按原版槽位顺序累加单精度填充率，然后用 26.2 的离散插值计算 0–15。双箱按右半部 27 槽、左半部 27 槽组合；没有分别对两半求和再合并，避免浮点舍入差异。

编辑器可放置、合并、拆分箱子，在检查面板选择槽位和默认物品，写入或清空数量。上方导电方块阻挡普通箱子开启及比较器读取；木桶不受这种阻挡。当前环境没有坐在箱子上的猫，不模拟相关 AI。

查看人数作为显式输入保留。手动打开/关闭容器将其切换为 1/0；内核接口也接受非负人数。陷阱箱输出限制在 0–15，并向下强充能；木桶更新 `open` 状态。恒定的外部查看人数无需每 5 gt 查找玩家实体，人数改变时立即执行相应器件更新。箱盖的显示由原生状态驱动，尚未实现原版连续开合动画。

## 接口与文件

`stimulate` 的 `inventory` 参数是部分槽位修改数组，例如：

```json
{"inventory":[{"slot":0,"item":"minecraft:stone","count":64}]}
```

接口槽号从 0 开始，界面从 1 开始。先验证整个数组，再修改库存；重复槽、数量越界和未知物品均报错。当前仅支持默认组件物品，非空 `components` 明确拒绝，不能用默认物品替代带组件的物品。

工程和运行快照使用物品 ID 名称与物理槽号保存，内部紧凑索引不会写入文件。恢复双箱时先还原两块的物理库存，再使用组合槽位读取。

## 验证

`captureContainers.py` 在原版运行 17 刻、14 个观测点，覆盖不同堆叠上限、满/空容器、双箱读数与拆分、箱盖阻挡、木桶状态和陷阱箱短时查看人数。原生测试另外覆盖自动合并、物理槽序、空/非空库存快照和无效批量修改的原子性。

新增 `captureHoppers.py` 的 65 刻 / 25 点原版对照，逐格比较方块状态、模拟读数及每个物理槽的物品与数量，覆盖正反搭建顺序、跨区块链、先推后拉、锁定、满箱、阻挡箱盖、拆除重放置和输入容器唤醒。拆除场景先清空库存，避免把原版随机散落的掉落物混入容器传输测试。

## 漏斗与休眠

漏斗具有真实五槽库存，每次成功工作后冷却 8 gt，先向朝向的容器推出一件，再从上方容器吸入一件。锁定阻止自身工作，其他漏斗仍能向其传入或从中取出；箱盖阻挡不影响漏斗访问。当前只支持默认物品的合并及已开放容器，不包含实体容器、掉落物运动/吸入或加工槽的方向过滤。

原版 `Level.tickBlockEntities` 按注册顺序执行方块实体。内核为漏斗、阳光探测器和运动活塞保留固定序号，方块状态变化不会重新排序；移除后重新放置获得新序号。向空漏斗传入物品时，接收方是否已在当刻执行，对应原版 7/8 冷却差异，不能统一改成从下一刻再等 8 gt。

无可用输入、满输出或锁定的漏斗在没有可观察重试副作用时休眠。库存变化、容器拓扑变化及供电变化局部唤醒相关漏斗，恢复后仍按固定序号执行；冷却以绝对到期刻保存。对普通容器取物失败会经历移除/恢复并可能通知比较器，这类重试保留逐刻执行。5,000 空漏斗检查后推进到第 1,000,000 gt 不产生额外计划事件，随后添加库存、容器或解除锁定仍可传输；这只是空闲优化验证，不作为活动电路 TPS。

运行快照保存序号、冷却和唤醒队列，并验证其一致性。旧预览快照若含方块实体事件却缺少固定顺序，明确拒绝恢复，须从电路工程重新运行；不根据队列临时顺序猜测精确续跑。电路工程也保留存活实体的注册顺序。

浏览器的“漏斗实验”提供箱子—漏斗链—木桶、锁定拉杆及比较器读出，可直接操作五槽库存、运行或逐刻观察。
