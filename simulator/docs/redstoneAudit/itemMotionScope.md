# 掉落物运动与「抛出再吸收」闭环的范围说明

对应 issue #12 验收里的最后一项：**抛出再吸收**。本文件是**范围设计与影响说明**，
不是实现记录；按 AGENTS 的约定，重大范围变更先写设计再决定是否实施。

## 现状

两个半边都已经存在，缺的是中间那一段：

| 半边 | 状态 |
|---|---|
| 投掷器抛出 | 已实现并有原版差分。`itemEjected` 外部动作记录序号、游戏刻、同刻顺序、源坐标、物品、数量、**初始位置与速度**；位置与速度用原版随机算法计算，`java26_2DropperMotion` 逐位对照 36 组浮点位模式。 |
| 漏斗吸取掉落物 | 已实现并有原版差分（`java26_2HopperPickup`）。两条原版路径都在：`suckInItems` 的实体分支与 `HopperBlock.entityInside`。 |
| **中间：掉落物从抛出点运动到被吸取的位置** | **未实现**。 |

也就是说，闭环目前依赖外部模型：用户拿到 `itemEjected` 的初始位置与速度，自己算出落点，
再用 `stimulate(漏斗, {"groundItems": [...]})` 声明结果。器件两端都是原版验证过的，
中间那一段没有建模，因此**不能称为「真实自动世界行为」**。

## 要做到真正自动闭环，原版需要什么

逐条来自 `net/minecraft/world/entity/item/ItemEntity.java` 的 `tick()`：

1. **重力与阻力**：`getDefaultGravity() = 0.04`；每刻 `move(SELF, delta)` 之后
   `delta *= (airDrag, airDrag, airDrag)`，落地时水平再乘方块摩擦
   `getBlockPosBelowThatAffectsMyMovement()` 的 `Block.getFriction()`，
   且落地时 `delta.y *= -0.5`（弹跳）。
2. **碰撞求解**：`Entity.move` 是对**体素碰撞形状**的扫掠求解，不是「整块或空气」。
   内核目前的注册表只导出 `fullCube`（`isCollisionShapeFullBlock`）、支撑掩码与刚性掩码，
   **没有逐状态的碰撞体素**。台阶、楼梯、栅栏、漏斗自身的漏斗形都会改变落点。
3. **卡住挤出**：`noPhysics = !level.noCollision(...)` 时调用 `moveTowardsClosestSpace`，
   把卡在碰撞形状里的掉落物推到最近空位。这条已经在 `entityIoProtocol.md` 里作为
   「协议不建模，声明的位置应当在自由空间里」记录过，实测也踩到过。
4. **合并**：`tickCount % rate == 0` 时 `mergeWithNeighbours()`，
   `rate` 取 2 或 40，取决于**这一刻方块坐标有没有变**；合并范围是包围盒水平膨胀 0.5。
5. **静止快路径**：`onGround() && 水平速度平方 < 1e-5 && (tickCount + getId()) % 4 != 0`
   时**跳过** `move`。注意它依赖 `getId()`——实体的全局自增编号。
   也就是说，要逐刻对齐，实体身份（分配顺序）必须进入模型状态。
6. **流体、方块效果、寿命**：水/岩浆里的 `setFluidMovement`、
   `applyEffectsFromBlocks`（仙人掌、篝火等）、`age >= 6000` 消失、`pickupDelay`。
7. **实体阶段顺序**：掉落物在 `ServerLevel` 的实体阶段执行，早于方块实体阶段；
   多个掉落物之间的顺序来自实体列表。内核目前只有阶段 3 的「接触」事件，
   没有按实体列表排序的实体阶段。

## 三个可选范围

### 方案一（最小，建议先做）：把闭环停在协议层，但让它可被验证

不建模运动。改动只有两处：

- 让差分重放能**消化 `itemEjected` 外部动作**（现在内核按 R11 约定暂停，
  `checkReference` 无法继续，所以「投掷器朝空气抛出」的场景根本跑不完，这一点实测踩到过）。
  做法是在重放里按记录顺序确认动作，等价于界面上的「确认已处理」。
- 增加一个场景：投掷器朝空气抛出 → 外部模型（场景脚本）按 `itemEjected` 的落点声明
  `groundItems` → 漏斗吸走。两端都与原版对照，中间那一步**明示为外部输入**。

代价小；给出的结论是「两端各自正确且能组合」，**不是**「世界会自动这样做」。

### 方案二（中等）：受限运动模型，前提不满足就明确拒绝

只在「路径上只有整方块或空气」的环境里模拟自由落体 + 摩擦 + 弹跳，
不做流体、方块效果、合并与挤出。运行前检查前提（路径经过的格子必须是
`fullCube` 或空气），不满足就**报错停下**，而不是给出一个看似合理的落点。

还需要引入实体身份与实体阶段（第 5、7 条），否则静止快路径与多实体顺序对不齐。
这已经是一个新的子系统，需要单独的验收与原版差分。

### 方案三（完整）：逐状态碰撞体素 + 完整实体阶段

导出每个方块状态的碰撞体素形状，实现扫掠碰撞、流体、合并、方块效果、寿命与实体编号。
这是「真实自动世界行为」的门槛，也是明确的重大范围扩展，
需要在实施前单独确认（性能、存档格式、界面都会受影响）。

## 建议

先做**方案一**，把 #12 的「抛出再吸收」明确记成
「器件两端已验证 + 中间为外部输入」，并在 issue 与文档里如实写清它不是自动闭环。
方案二/三属于新的范围扩展，需要用户明确决定后再排期；
本文件不把它们当成已决定的事项，也不把「不做」写成用户的决定——
AGENTS 里明确排除的是 TNT 复制机、流体农场、矿车计算机和依赖生物 AI 的机器，
**掉落物运动本身没有被排除**。
