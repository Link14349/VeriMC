# 堆肥桶

支持 26.2 的 115 种默认堆肥材料、概率升层、第七层成熟计时、比较器输出，以及上方漏斗/投掷器投料和下方漏斗取骨粉。堆肥桶没有持久物品库存，容器访问按当前层数临时提供输入槽或骨粉输出槽。

## 投料与成熟

环境面板选择物品，点击“投入一件”；接口为：

```json
{"compostItem":"minecraft:pumpkin_pie"}
```

每次输入代表一次物品投入。第 0 层的有效材料保证成功，不消耗随机数；第 1–6 层调用一次世界 `nextDouble` 与原版单精度概率比较，即使概率为 100% 也保留抽样。未升层仍消耗这一件物品。普通不可堆肥物品是无效操作，未知 ID 报错；第 7–8 层不再接收材料。失败投料推进的随机状态同样支持撤销、重做和快照。

到达第 7 层后安排 20 gt 的成熟计划刻，到期变为第 8 层。直接放置第七层也会排期；先改成其他层再改回第七层时，保留此前已有的计划刻。成功投料和取空产生 `BLOCK_CHANGE` 振动，成熟变化本身不发出该游戏事件。

比较器输出等于 0–8 层数；堆肥桶自身没有直接供电。空闲、未满与已成熟状态都不逐刻扫描，只有等待成熟时保留一个计划事件。

## 方向和临时容器

输入槽只对上面开放，输出骨粉只对下面开放。其他方向的漏斗/投掷器不能插入；即使第七层容器没有槽，投掷器仍把它识别为容器，不向外抛出物品。有效输入失败升层也算一次成功传输，漏斗正常进入 8 gt 工作冷却。

保留原版临时输出容器的特殊行为：下方漏斗五槽均为其他物品、却未达到各自堆叠上限时，抽取尝试会清空成熟堆肥，但骨粉无法进入漏斗。原因是原版临时槽的移除回调先把方块置空，失败后恢复临时槽并不会恢复方块层数。五槽真正满载时不会尝试抽取，堆肥仍为第八层。这两种情况均经过原版逐刻对照，不能通过提前检查容量把它们合并成一种行为。

运行快照保留方块层数、成熟计划、世界随机源和相关漏斗状态；没有虚构的堆肥桶方块实体或长期库存。当前环境只模拟显式投料与容器传输，不模拟玩家背包、手动取骨粉的掉落实体、声音、粒子或村民行为，器件标记部分支持。原版填充粒子的随机调用发生在客户端，不额外消耗服务端世界随机源。

## 验证

来源为固定 Java 26.2 的 `ComposterBlock`、`SimpleContainer`、`HopperBlockEntity` 与 `DropperBlock`。

- `ExportComposting.java` 导出 115 种材料概率，并生成 4,176 次原版隔离投料记录，覆盖 0–8 层、四种种子和不可堆肥的石头，逐一核对层数、物品消耗与随机源状态。
- `captureComposters.py`：111 刻 / 26 点，六方向投掷器、漏斗连续投料、成熟后重启、成功与失败骨粉抽取、满载休眠、重复进入第七层及振动。
- 原生测试覆盖成熟中快照、空闲推进、未知输入原子拒绝及失败抽取；Release / ASAN / UBSAN 共 82 项通过。
- `composterTests.py` 及库存、唱片机、投掷器、振动和完整服务协议回归通过。浏览器手工放置、连续投入七件、层数探针以及第 20 gt 成熟为 8 通过，控制台无错误。

游戏 JAR、反编译源码及客户端资源不随项目分发。
