# 方块计划刻与单步执行

兼容目标是固定的 Java 26.2、所有模拟区域保持加载。实现位于 `blockTicks.cpp`，依据已校验服务端中的 `LevelTicks`、`LevelChunkTicks` 和 `ScheduledTick`；每刻上限 65,536 来自 `ServerLevel.tick` 的实际调用参数。

## 收集与执行

1. 每个水平 16×16 区块维护自己的计划队列，依次按目标游戏刻、优先级、加入序号排序。Y 坐标不划分计划队列。
2. 取出所有已经到期的区块队首，在这些队首之间按优先级、加入序号选择。积压时不能把所有事件简单按目标时间全局排序。
3. 一次收集至多 65,536 项，然后才执行这一批。收集时即从未来计划集合移除，当前执行项也先从批次移除再调用器件逻辑。
4. 批次运行期间新安排的零延迟计划最早在下一游戏刻收集。超过本刻上限的事件保留原目标时间，并在下一刻继续参与区块排序。

`hasScheduled` 只查询未来队列；`willTick` 只查询本刻剩余批次。同一个坐标和方块类型可以同时各有一个未来计划和一个本刻事件。侦测器使用前者，火把、中继器和比较器的邻居检查使用后者。即使重复计划被拒绝，加入序号仍会递增。

核心只为有计划的区块分配队列。到期区块索引用有序队首集合，避免每刻扫描全部区块；索引调整仅发生在队首改变时。它只改变查找到期区块的方法，不改变原版的收集或执行顺序。方块实体和活塞方块事件仍由独立阶段处理，方块实体采用持久注册顺序。

绊线输入驱动另有外部接触阶段，位于方块事件之后、方块实体之前。文件中阶段编号为 3，排序位置由阶段映射确定；编号 2 仍代表原有方块实体阶段，避免旧快照字段含义改变。该阶段仅用于受控接触重试，详细边界见 [绊线说明](tripwire.md)。

## 暂停与快照

事件单步可以停在本刻批次中途。运行快照的 `events` 保存未来计划和其他阶段事件，`blockTickState.batch` 按顺序保存本刻剩余计划，`earliestCollection` 保存下一次允许收集的刻。克隆、撤销和文件恢复都保留这一区别。导入验证两个集合各自的去重约束与全局加入序号，失败时不改变当前世界。

旧版快照若含已到本刻的方块计划却没有批次数据，将明确拒绝恢复；可以从电路文件重新运行。空闲跳跃完成后，也会推进收集边界，因此外部输入安排的零延迟计划不会倒回已经结束的阶段。

## 证据与边界

- `ExportScheduler.java` 直接调用原版队列，记录 21 刻内跨正负区块、不同优先级、积压、限制、回调续排和查询结果。独立 C++ 对照执行顺序与两个集合的成员关系。
- `captureTickBatches.py` 在原版 GameTest 放置四组面对面侦测器，包括区块边界及负坐标，记录 25 刻 / 8 点。
- 原生测试覆盖 65,537 个到期事件的跨刻分批、空闲后的零延迟计划，以及本刻与未来队列含相同位置时逐事件保存恢复。

未实现区域卸载、保存后重新加载区块的原版负序号分配，也不模拟服务端其他维度的调度。本测试证据不延伸为所有更新顺序敏感机器的兼容声明。
